# Architecture Snapshot

Generated by Codex from code inspection on 2026-05-05. Treat this file as the current working map of the project. Some older Markdown files may be stale; prefer this snapshot plus direct code checks for changed areas.

## Repository Shape

- `cursor_sh/` is the main product application.
  - `cursor_sh/src/` is the Vue SPA for the landing page, customer workspace, admin console, staff console, and contractor console.
  - `cursor_sh/backend/` is the main FastAPI backend.
  - `cursor_sh/src/website/` is the landing page embedded into the main SPA at `/`.
- `website/` is a standalone Vue/Vite landing-site version. It appears optional or historical because the main Docker compose does not run it.
- `ai_backend/` is a lightweight standalone AI requirement-collection service. It appears older/secondary; the main system uses AI routes inside `cursor_sh/backend/app/api/`.
- Root `docker-compose.yml` deploys the main backend and main frontend.

## Main Frontend

Path: `cursor_sh/`

Stack:

- Vue 3
- Vite
- TypeScript
- Pinia
- Vue Router
- Element Plus
- SCSS
- GSAP for landing-page animation

Entrypoints:

- `cursor_sh/src/main.ts`: creates the Vue app, registers Pinia, router, Element Plus, global icons, and `styles/main.scss`.
- `cursor_sh/src/App.vue`: thin shell with only `<router-view />`.
- `cursor_sh/src/router/index.ts`: central route map and role guard.
- `cursor_sh/src/utils/request.ts`: Axios instance using `baseURL: /api`, Bearer token injection, and unified `ApiResponse` handling.
- `cursor_sh/src/utils/api.ts`: typed-ish API facade for auth, orders, staff, notifications, announcements, enterprise review, contractor management, workflow config, and chat history.

Primary route groups:

- `/`: embedded landing page from `src/website/LandingPage.vue`.
- `/login`, `/register`: customer auth.
- `/admin/login`: admin auth.
- `/user/*`: customer workspace.
  - workspace
  - video marketplace
  - create/edit order
  - orders and order detail
  - profile
  - drafts
- `/admin/*`: admin dashboard.
  - order management and order detail
  - staff management
  - announcement management
  - enterprise review
  - contractor management
  - workflow config
  - AI chat records
  - customer management
- `/staff/*`: staff/designer dashboard.
  - assigned order list
  - assigned order detail
  - profile
- `/contractor/register`, `/contractor/login`: contractor public auth/register pages.
- `/contractor/*`: contractor dashboard.
  - assignments
  - assignment detail
  - profile

Auth/role behavior:

- Pinia auth store persists `token` and `user` to `localStorage`.
- Router guards check `requiresAuth` and role-specific access.
- Supported roles are `admin`, `user`, `staff`, and `contractor`.

Notes:

- `utils/api.ts` still contains old `taskApi` and mock branches, but `ENABLE_MOCK = false`, so the real backend is the active path.
- Prefer adding new frontend API methods in `utils/api.ts` and route/page behavior in the relevant `views/*` area.

## Main Backend

Stack:

- FastAPI
- SQLAlchemy async
- SQLite for default local development
- MySQL/RDS support via `DATABASE_URL` or `DB_TYPE=mysql`
- Pydantic / pydantic-settings
- JWT with `python-jose`
- Loguru
- SlowAPI rate limiting
- ReportLab PDF generation
- Optional Aliyun OSS

Entrypoints:

- `cursor_sh/backend/app/main.py`: FastAPI app setup, middleware, static mounts, route registration, startup initialization.

- `cursor_sh/backend/app/database.py`: async engine/session and `Base.metadata.create_all`.
- `cursor_sh/backend/app/audit_database.py`: separate audit database setup.

Deployment modes:

- `DEPLOYMENT_MODE=all`: development/full mode.
- `DEPLOYMENT_MODE=external`: customer-facing routes such as AI chat and ASR.
- `DEPLOYMENT_MODE=internal`: internal system routes such as staff, contractor admin, workflow, admin memory.

Always/common route areas:

- `/api/auth`
- `/api/upload`
- `/api/orders`
- `/api/notifications`
- `/api/announcements`
- `/api/logs`
- `/api/enterprise`
- `/api/ai/chat-history`

External route areas:

- `/ai/*`
- `/api/asr/*`

Internal route areas:

- `/api/staff`
- `/api/contractor`
- `/api/contractor-admin`
- `/api/workflow-config`
- `/api/admin/memory`

Startup behavior:

- Initializes log system.
- Creates/initializes main business database.

- Initializes isolated audit database.
- In `all` or `internal`, ensures initial admin and default workflow stages.
- Ensures upload directory when OSS is disabled.

## Data And Permission Model

Roles are stored in separate tables:

- `users`: customer accounts.
- `admins`: admin accounts.
- `staff_members`: internal staff/designer accounts.
- `contractors`: contractor accounts.

JWT payload includes `user_id` and `role`. Backend dependency resolution in `app/utils/dependencies.py` uses the role to choose which table to query.

Important dependency helpers:

- `get_current_user`
- `require_admin`
- `require_admin_or_staff`
- `require_contractor`
- `require_internal_user`

Because users/admins/staff/contractors are separate tables, some models intentionally use string IDs without strict foreign keys for cross-role relationships.

## Core Business Domain

The system manages AI/VR/naked-eye-3D content orders.

Order model:

- File: `cursor_sh/backend/app/models/order.py`
- Main table: `orders`
- Order data specific to each order type is stored in `order_data` JSON.
- `design_plan` JSON stores admin-created design plans before contractor assignment.

Order types:

- `video_purchase`: naked-eye 3D finished-video purchase/adaptation.
- `ai_3d_custom`: AI naked-eye 3D custom content.
- `digital_art`: digital art custom content.

Order statuses:

- `draft`
- `pending_assign` legacy compatibility state
- `pending_contract`
- `in_production`
- `pending_review`
- `preview_ready`
- `review_rejected`
- `revision_needed`
- `final_preview`
- `completed`
- `cancelled`

Order-related capabilities:

- Customer creates drafts or submits orders.
- Customer uploads scene photos/materials.
- System can generate order confirmation PDFs and email them.
- Admin/staff can view and manage orders.
- Admin can assign responsible staff.
- Staff can upload initial/final previews.
- Admin can review previews.
- Customer can approve or request revisions.
- Admin can advance contract/payment state and cancel orders with SMS verification.
- Notifications are generated around important order events.

## Contractor Production Workflow

Contractor models:

- `contractor.py`: contractor account.
- `contractor_invitation.py`: invitation tokens/links.
- `contractor_assignment.py`: assignment of an order to a contractor.
- `contractor_deliverable.py`: staged deliverables and review state.
- `workflow.py`: configurable workflow stages.

Workflow concept:

- Admin configures global stages such as plan, original art, model, render, final video.
- Admin assigns an order to one contractor.
- Assignment includes a generated schedule based on workflow stage defaults.
- Contractor can accept or reject.
- Contractor submits deliverables per stage.
- Deliverables support:
  - draft/submitted/admin-approved/admin-rejected statuses
  - version history through `parent_id`
  - files JSON
  - description
  - self-review checks
  - admin review note
  - publish-to-user flag and note
  - admin comments visible to contractor
- Admin can review deliverables, publish approved deliverables to the customer, and advance stages.

## Deployment And Local Run

Local combined dev:

- Script: `scripts/start_system.sh`
- Frontend: `cursor_sh`, Vite dev server at `http://localhost:3000`
- Backend: `cursor_sh/backend`, Uvicorn at `http://localhost:8000`
- API docs: `http://localhost:8000/docs`

Frontend Vite proxy:

- `/api` -> `127.0.0.1:8000`
- `/api/asr` -> `127.0.0.1:8000`, websocket enabled
- `/ai` -> `127.0.0.1:8000`
- `/uploads` -> `127.0.0.1:8000`

Docker full stack:

- Root `docker-compose.yml`
- `backend` builds `./cursor_sh/backend`
- `frontend` builds `./cursor_sh`
- frontend exposes `8080:8080`
- Nginx proxies `/api`, `/ai`, `/uploads`, and `/static` to backend.
- Volumes persist backend data, uploads, and logs.

## Maintenance Notes For Future Codex Work

When changing code later, start from this file, then inspect only the touched module and its immediate API/model/service dependencies.

Likely main paths:

- Main frontend: `cursor_sh/src`
- Main backend: `cursor_sh/backend/app`
- Main deployment: root `docker-compose.yml`

Likely legacy or secondary paths:

- Root `ai_backend`
- Root `website`
- `taskApi` and old task types in `cursor_sh/src/utils/api.ts` and `cursor_sh/src/types/index.ts`
- Patch/fix scripts unless the task is deployment recovery.

Areas that deserve care:

- Role handling is split across multiple account tables.
- Cross-role references often use string IDs instead of strict FK constraints.
- Some DB migrations run during app startup; check startup side effects before changing models.
- `order_data` is JSON and stores type-specific order fields, so frontend/backend shape mismatches may not fail at schema level until runtime.
- AI routes include several agent modules under one `/ai` router; confirm exact endpoint before editing chat behavior.
- There are duplicate landing-page assets and components between `cursor_sh/src/website` and root `website`.
